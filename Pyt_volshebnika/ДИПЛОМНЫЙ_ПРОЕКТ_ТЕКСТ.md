# ВВЕДЕНИЕ

## Актуальность темы

В современном мире цифровых технологий игровая индустрия демонстрирует устойчивый рост, охватывая всё новые сферы человеческой деятельности. Особое место занимают образовательные и развлекательные веб-приложения, которые сочетают в себе интерактивность, вовлечённость и возможность персонализации пользовательского опыта. Геймификация процессов обучения и тестирования становится мощным инструментом для достижения образовательных целей, повышения мотивации пользователей и улучшения усвоения информации.

Тема дипломного проекта «Разработка интерактивного веб-приложения "Путь Волшебника" с системой генерации персонализированного контента на основе искусственного интеллекта» актуальна по нескольким причинам. Во-первых, растущий спрос на интерактивные развлекательные системы требует создания качественных веб-приложений с глубоким погружением пользователя в игровой процесс. Во-вторых, интеграция искусственного интеллекта для генерации персонализированного контента открывает новые возможности для адаптации игрового опыта под индивидуальные характеристики каждого пользователя. В-третьих, развитие современных веб-технологий (React, TypeScript, Node.js) позволяет создавать высокопроизводительные кроссплатформенные решения, доступные широкой аудитории без необходимости установки дополнительного программного обеспечения.

Проект вносит вклад в развитие специальности 09.02.07 «Информационные системы и программирование» и соответствующей отрасли информационных технологий, демонстрируя практическое применение современных архитектурных паттернов, технологий работы с базами данных (PostgreSQL, Drizzle ORM), а также интеграции с API искусственного интеллекта (OpenAI GPT-4) для генерации уникального нарративного контента.

## Цели и задачи

**Цель дипломного проекта** — разработка интерактивного веб-приложения «Путь Волшебника», реализующего систему прохождения квестов с динамическим изменением характеристик персонажа и генерацией персонализированного предсказания архетипа волшебника на основе искусственного интеллекта.

Для достижения поставленной цели необходимо решить следующие **задачи**:

1. **Провести анализ предметной области** — изучить существующие решения в области интерактивных веб-игр, определить требования к функциональности и пользовательскому интерфейсу.

2. **Разработать архитектуру приложения** — спроектировать структуру веб-приложения с разделением на клиентскую часть (frontend) и серверную часть (backend), определить схему взаимодействия между компонентами системы.

3. **Спроектировать базу данных** — разработать схему реляционной базы данных для хранения информации о пользователях, их характеристиках, пройденных квестах и полученных архетипах.

4. **Реализовать клиентскую часть приложения** — создать пользовательский интерфейс с использованием библиотеки React, реализовать анимации переходов, систему отображения диалогов и квестовых сценариев.

5. **Реализовать серверную часть приложения** — разработать REST API для обработки запросов клиента, реализовать логику расчёта архетипов, обеспечить интеграцию с базой данных.

6. **Интегрировать API искусственного интеллекта** — настроить взаимодействие с OpenAI API для генерации уникальных предсказаний архетипов на основе характеристик пользователя.

7. **Провести тестирование системы** — выполнить функциональное тестирование всех компонентов приложения, обеспечить корректность работы системы в различных сценариях использования.

# Глава 1. Анализ и постановка задачи

## 1.1. Описание предметной области

Предметная область дипломного проекта связана с разработкой интерактивных развлекательных веб-приложений с элементами геймификации и повествовательного сторителлинга. Данная сфера деятельности охватывает создание цифровых продуктов, которые сочетают в себе игровые механики, нарративный контент и персонализированный пользовательский опыт.

**Основная цель** разработки подобных систем — предоставление пользователю иммерсивного опыта прохождения интерактивного сценария с возможностью влияния на результат через принятие решений. В контексте проекта «Путь Волшебника» речь идёт о создании образовательного развлекательного приложения, где пользователь проходит серию испытаний (квестов), делая моральные и этические выборы, которые влияют на характеристики персонажа и итоговый результат.

**Участники процесса:**
1. **Пользователь (игрок)** — основной участник, который проходит регистрацию, авторизацию, выбирает аватар, проходит квесты и получает результат в виде архетипа волшебника.
2. **Система (веб-приложение)** — автоматизированная система, которая обрабатывает действия пользователя, хранит данные, рассчитывает характеристики и генерирует персонализированный контент.
3. **Администратор** — лицо, ответственное за поддержку работоспособности системы, мониторинг базы данных и управление контентом.

**Объекты обработки информации:**
- Данные пользователя (имя, пароль, аватар);
- Характеристики персонажа (сострадание, смелость, мудрость, амбиции, принципиальность);
- Информация о пройденных квестах;
- Выборы пользователя в каждом квесте;
- Итоговый архетип и текстовое предсказание;
- История предыдущих прохождений.

**Текущее состояние предметной области:**

В настоящее время существует множество платформ для создания интерактивных историй и текстовых квестов. Однако большинство из них имеют следующие недостатки:
- **Отсутствие персонализации** — пользователи получают одинаковый контент независимо от своих выборов;
- **Линейность сценариев** — ограниченное количество ветвлений сюжета;
- **Отсутствие системы характеристик** — выборы пользователя не накапливают изменяемые параметры;
- **Статичность контента** — все пользователи видят одинаковые результаты;
- **Сложность масштабирования** — добавление нового контента требует значительных усилий разработчиков.

**Проблемы, требующие решения:**

1. **Проблема уникальности опыта.** Пользователи хотят получать персонализированный контент, который отражает их индивидуальные выборы и характеристики. Существующие решения часто предлагают ограниченный набор заранее заготовленных результатов.

2. **Проблема вовлечённости.** Для поддержания интереса пользователя необходима система, которая реагирует на его действия и предоставляет обратную связь в виде изменения характеристик и итоговой оценки.

3. **Проблема масштабируемости контента.** Ручное написание всех возможных вариантов предсказаний и результатов требует значительных временных затрат и ограничивает вариативность.

4. **Проблема технологической доступности.** Многие существующие платформы требуют установки дополнительного программного обеспечения или не поддерживают кроссплатформенный доступ.

**Необходимость разработки информационной системы:**

Разработка веб-приложения «Путь Волшебника» обусловлена необходимостью создания системы, которая:
- Предоставляет пользователю уникальный персонализированный опыт прохождения;
- Автоматически рассчитывает результат на основе многомерных характеристик;
- Генерирует уникальный текстовый контент с использованием искусственного интеллекта;
- Доступна через веб-браузер без установки дополнительного ПО;
- Поддерживает возможность повторного прохождения для получения других результатов.

## 1.2. Анализ существующих решений и аналогов

Для обоснования необходимости разработки собственной системы был проведён анализ существующих решений в области интерактивных веб-приложений и платформ для создания текстовых квестов.

**Критерии сравнения:**
1. Персонализация контента;
2. Система характеристик и влияний выборов;
3. Возможность генерации уникального контента;
4. Кроссплатформенность (веб-доступ);
5. Возможность повторного прохождения;
6. Открытый исходный код;
7. Стоимость внедрения и сопровождения.

### Анализ аналогов

**1. Twine**

**Назначение:** Twine — это инструмент с открытым исходным кодом для создания интерактивных нелинейных историй.

**Основные функции:**
- Визуальный редактор для создания связей между сценами;
- Поддержка переменных и условной логики;
- Экспорт в HTML-формат;
- Расширяемость через JavaScript.

**Преимущества:**
- Бесплатный инструмент с открытым исходным кодом;
- Низкий порог входа для начинающих авторов;
- Возможность публикации в вебе;
- Активное сообщество и множество ресурсов для обучения.

**Недостатки:**
- Ограниченная система переменных (нет встроенной системы характеристик);
- Весь контент должен быть написан вручную заранее;
- Отсутствие встроенной системы аналитики;
- Ограниченные возможности для персонализации;
- Примитивный интерфейс по умолчанию.

**2. Ink (Inklewriter)**

**Назначение:** Ink — это язык сценариев и движок для создания интерактивных нарративов, разработанный студией Inkle.

**Основные функции:**
- Специализированный язык сценариев;
- Интеграция с Unity и другими движками;
- Поддержка переменных и условий;
- Генерация веб-версий историй.

**Преимущества:**
- Мощный язык сценариев с поддержкой сложной логики;
- Интеграция с популярными игровыми движками;
- Хорошая документация;
- Поддержка сложной ветвящейся структуры.

**Недостатки:**
- Требует изучения специализированного языка;
- Нет встроенной системы генерации контента;
- Ограниченная персонализация для конечного пользователя;
- Требует технических знаний для развёртывания.

**3. ChoiceScript (Choice of Games)**

**Назначение:** ChoiceScript — это язык программирования для создания многовариантных текстовых игр с системой характеристик.

**Основные функции:**
- Встроенная система характеристик персонажа;
- Поддержка сохранений и достижений;
- Публикация на платформе Choice of Games;
- Монетизация через продажу игр.

**Преимущества:**
- Встроенная система характеристик и влияний;
- Возможность монетизации;
- Готовая платформа для публикации;
- Поддержка сложной игровой логики.

**Недостатки:**
- Закрытая экосистема (требуется публикация на Choice of Games);
- Ограниченный контроль над распространением;
- Весь контент пишется вручную;
- Нет интеграции с ИИ для генерации контента.

**4. Ren'Py**

**Назначение:** Ren'Py — это движок для создания визуальных новелл и симуляторов жизни.

**Основные функции:**

# Глава 2. Проектирование и реализация

## 2.1. Проектирование программного продукта

### 2.1.1. Описание и обоснование архитектуры системы

**Тип архитектуры:** Клиент-серверная трёхуровневая архитектура с разделением на:
1. **Уровень представления (Presentation Layer)** — клиентское React-приложение;
2. **Уровень бизнес-логики (Business Logic Layer)** — сервер Express.js;
3. **Уровень данных (Data Layer)** — база данных PostgreSQL.

**Обоснование выбора архитектуры:**

Выбор трёхуровневой клиент-серверной архитектуры обусловлен следующими факторами:

1. **Разделение ответственности.** Каждый уровень отвечает за свою задачу:
   - Клиент отображает интерфейс и обрабатывает взаимодействие с пользователем;
   - Сервер обрабатывает бизнес-логику и валидацию;
   - База данных хранит и предоставляет данные.

2. **Масштабируемость.** Уровни можно масштабировать независимо:
   - Клиентская часть обслуживается через CDN;
   - Серверная часть может быть размножена через балансировщик нагрузки;
   - База данных может быть реплицирована.

3. **Безопасность.** Разделение уровней позволяет:
   - Изолировать базу данных от прямого доступа извне;
   - Реализовать аутентификацию на серверном уровне;
   - Валидировать все входные данные на сервере.

4. **Поддерживаемость.** Изменения на одном уровне минимально влияют на другие.

**Структура системы:**

**Рисунок 1 — Архитектура приложения**

**Описание компонентов:**

**Клиентская часть (React):**
- **Pages** — страницы приложения (IntroPage, AuthPage, GameScreen, FinalPage);
- **Components** — переиспользуемые UI-компоненты (кнопки, карточки, диалоги);
- **Hooks** — хуки для управления состоянием и запросами к API;
- **Lib** — вспомогательные утилиты (аудио, квесты, стили).

**Серверная часть (Express.js):**
- **Routes** — определение конечных точек API;
- **Controllers** — обработчики запросов;
- **Middleware** — промежуточное ПО (CORS, парсинг JSON, аутентификация);
- **OpenAI Integration** — модуль интеграции с API искусственного интеллекта.

**База данных (PostgreSQL):**
- **players** — таблица пользователей;
- **quests** — таблица квестов (опционально, квесты могут быть захардкожены);
- **quest_choices** — таблица выборов в квестах (опционально).

**Протокол взаимодействия:**

Взаимодействие между клиентом и сервером осуществляется по протоколу **HTTP/HTTPS** с использованием **REST API**. Все запросы и ответы передаются в формате **JSON**.

**Примеры конечных точек API:**
- `POST /api/auth/register` — регистрация пользователя;
- `POST /api/auth/login` — авторизация пользователя;
- `GET /api/players/:id` — получение данных игрока;
- `POST /api/players/:id/stats` — обновление характеристик;
- `POST /api/archetype-text` — генерация предсказания архетипа.

**Альтернативные архитектурные решения:**

Рассматривалась **микросервисная архитектура**, однако она была отклонена по следующим причинам:
- Избыточная сложность для проекта с одним основным сервисом;
- Дополнительные накладные расходы на межсервисную коммуникацию;
- Усложнение развёртывания и отладки.

Была выбрана **монолитная архитектура с модульной организацией кода**, которая:
- Проще в разработке и поддержке;
- Требует меньше ресурсов для развёртывания;
- Позволяет легко выделить отдельные сервисы при необходимости масштабирования.

**Целостность данных:**

1. **Первичный ключ (PRIMARY KEY):** Поле `id` автоматически инкрементируется и уникально для каждой записи.

2. **Ограничения NOT NULL:** Все обязательные поля имеют ограничение NOT NULL, что предотвращает создание записей с отсутствующими данными.

3. **Значения по умолчанию (DEFAULT):** Поля характеристик и массивов имеют значения по умолчанию, что упрощает создание новых записей.

4. **Транзакции:** Все операции обновления характеристик выполняются в транзакциях, что гарантирует атомарность изменений.

5. **Каскадные обновления:** Поле `updated_at` автоматически обновляется при изменении записи.

**Нормализация:**

Таблица `players` находится в **третьей нормальной форме (3NF)**:
- Все поля атомарны (1NF);
- Все неключевые поля полностью зависят от первичного ключа (2NF);
- Отсутствуют транзитивные зависимости (3NF).

**Индексация:**

Для повышения производительности предусмотрены следующие индексы:
- **Первичный ключ `id`** — автоматически создаётся кластерный индекс;

**1. Расчёт архетипа (GameScreen.tsx):**

```typescript
function calculateArchetype(
  compassion: number,
  courage: number,
  wisdom: number,
  ambition: number,
  principle: number
): string {
  // Считаем количество отрицательных характеристик
  const negativeCount = [compassion, courage, wisdom, ambition, principle]
    .filter(v => v < 0).length;

  // Если ≥3 отрицательных → Изгой
  if (negativeCount >= 3) {
    return "Изгой";
  }

  // НАСТАВНИК: ВСЕ >= 6
  if (compassion >= 6 && courage >= 6 && wisdom >= 6 && 
      ambition >= 6 && principle >= 6) {
    return "Наставник";
  }

  // МРАК: Амбиции >= 7 И Сострадание <= 3
  if (ambition >= 7 && compassion <= 3) {
    return "Мрак";
  }

  // ВЛАСТИТЕЛЬ: Амбиции >= 6 И Сострадание >= 5
  if (ambition >= 6 && compassion >= 5) {
    return "Властитель";
  }

  // ЦЕЛИТЕЛЬ: Сострадание >= 6 И Смелость <= 4
  if (compassion >= 6 && courage <= 4) {
    return "Целитель";
  }

  // БОРЕЦ ЗА ПОРЯДОК: Принципиальность >= 6 И Сострадание <= 4
  if (principle >= 6 && compassion <= 4) {
    return "Борец за порядок";
  }

  // Если ничего не подошло → Изгой
  return "Изгой";
}
```

**Пояснение:** Функция реализует многоуровневую логику определения архетипа:
1. Проверка на «Изгоя» (≥3 отрицательных характеристик);
2. Проверка строгих условий для каждого архетипа;
3. Проверка мягких условий (сниженный порог);
4. Определение по доминирующей характеристике;
5. Возврат «Изгоя» по умолчанию.

**3. Обновление характеристик (api-server routes):**

```typescript
// apps/api-server/src/routes/players.ts
router.post("/players/:id/stats", async (req, res) => {
  const { playerId } = req.params;
  const {
    compassionDelta,
    courageDelta,
    wisdomDelta,
    ambitionDelta,
    principleDelta,
    questId,
    archetypeEarned,
  } = req.body;

  const player = await db.query.playersTable.findFirst({
    where: eq(playersTable.id, Number(playerId)),
  });

  if (!player) {
    res.status(404).json({ message: "Игрок не найден" });
    return;
  }

  // Обновление характеристик
  const updatedPlayer = await db
    .update(playersTable)
    .set({
      compassion: player.compassion + (compassionDelta || 0),
      courage: player.courage + (courageDelta || 0),
      wisdom: player.wisdom + (wisdomDelta || 0),
      ambition: player.ambition + (ambitionDelta || 0),
      principle: player.principle + (principleDelta || 0),
      completedQuests: JSON.stringify([
        ...JSON.parse(player.completedQuests),
        questId,
      ]),
      archetypeEarned: archetypeEarned ?? player.archetypeEarned,
      previousArchetypes: archetypeEarned
        ? JSON.stringify([...JSON.parse(player.previousArchetypes), archetypeEarned])
        : player.previousArchetypes,
      updatedAt: new Date(),
    })
    .where(eq(playersTable.id, Number(playerId)))
    .returning();

  res.json(updatedPlayer[0]);
});
```

**Пояснение:** Обработчик:
- Получает дельты характеристик из запроса;
- Находит игрока по ID;
- Обновляет характеристики с учётом дельт;
- Добавляет квест в список пройденных;
- Сохраняет архетип при получении;
- Возвращает обновлённые данные.

```typescript
function calculateArchetype(
  compassion: number,
  courage: number,
  wisdom: number,
  ambition: number,
  principle: number
): string {
  const negativeCount = [compassion, courage, wisdom, ambition, principle]
    .filter(v => v < 0).length;

  if (negativeCount >= 3) return "Изгой";
  if (compassion >= 6 && courage >= 6 && wisdom >= 6 && 
      ambition >= 6 && principle >= 6) return "Наставник";
  if (ambition >= 7 && compassion <= 3) return "Мрак";
  if (ambition >= 6 && compassion >= 5) return "Властитель";
  if (compassion >= 6 && courage <= 4) return "Целитель";
  if (principle >= 6 && compassion <= 4) return "Борец за порядок";
  
  return "Изгой";
}
```

router.post("/archetype-text", async (req, res) => {

  });

});

## Приложение В – Руководство пользователя и администратора

**РУКОВОДСТВО ПОЛЬЗОВАТЕЛЯ**

**1. Начало работы**

1.1. Откройте браузер и перейдите по адресу `http://localhost:5173`.

1.2. На странице авторизации введите имя и пароль.

1.3. Выберите аватар из предложенных вариантов.

1.4. Нажмите кнопку «НАЧАТЬ ПУТЬ».

**2. Прохождение квестов**

2.1. Прослушайте вступительное слово мастера (нажимайте Space/Enter для продолжения).

2.2. Выберите один из трёх порталов для начала испытания.

2.3. Читайте ситуацию и выбирайте один из вариантов ответа.

2.4. После каждого выбора вы увидите изменение характеристик.

2.5. Повторите для всех трёх квестов.

**3. Просмотр результатов**

3.1. После завершения всех квестов мастер предскажет ваш архетип.

3.2. Нажмите кнопку «Карта» для просмотра экзаменационной карты.

3.3. Для повторного прохождения нажмите «Пройти заново».

**РУКОВОДСТВО АДМИНИСТРАТОРА**

**1. Развёртывание**

1.1. Установите Node.js 20+, PostgreSQL 15+, pnpm 9+.

1.2. Клонируйте репозиторий и выполните `pnpm install`.

1.3. Настройте `.env` файл (DATABASE_URL, OPENAI_API_KEY).

1.4. Примените миграции: `pnpm db:push`.

1.5. Запустите сервер: `pnpm dev`.

**2. Мониторинг**

2.1. Проверка статуса: `GET /api/health`.

2.2. Просмотр логов: `pm2 logs`.

2.3. Резервное копирование: `pg_dump -U postgres Diplom > backup.sql`.

**3. Управление пользователями**

3.1. Просмотр пользователей: `SELECT * FROM players;`.

3.2. Сброс прогресса: `UPDATE players SET completed_quests='[]' WHERE id=1;`.

3.3. Удаление пользователя: `DELETE FROM players WHERE id=1;`.
